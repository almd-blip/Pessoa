3. Architectural Problem (why the migration output can't yet be the live read source) 


The Stage 2 migration transforms legacy state into WorkProduct[] on each load, but nothing transforms mutations back. Since §2 confirms Papers/Journeys funnel through exactly 6 App.tsx functions that call setPapers/setJourneys (writing only to scholar_papers/scholar_journeys), any edit made after the initial load is invisible to pessoa_work_products until the next reload re-runs the migration. If the UI read from pessoa_work_products as primary, a reload immediately after an edit would show correct data (migration re-derives fresh each time) — but within a session, before any reload, pessoa_work_products would already be stale relative to live state. Worse, if a future feature ever read pessoa_work_products mid-session (e.g. a Stage 3 project view), it would silently show outdated content. This isn't a bug in the migration — it did exactly what a one-time/per-load transformation is supposed to do — it's a structural gap: no mutation path currently writes to the new representation.

PROPOSAL — a thin module (natural home: replacing/absorbing src/lib/workProductMigration.ts's write responsibilities) with exactly two operations:


function loadWorkProducts(): WorkProduct[] // reads pessoa_work_products function saveWorkProducts(items: WorkProduct[]): SaveResult // writes pessoa_work_products 


App.tsx calls saveWorkProducts in a useEffect keyed on workProducts (replacing today's useEffects that write scholar_papers/scholar_journeys directly) — the same pattern already in use, just retargeted at one key instead of two. The adapter's only job is the localStorage read/write and defensive parsing (already implemented in Stage 2's readWorkProducts/write logic) — it has no knowledge of kind, Paper, or ResearchJourney. 11. Failure and Consistency Model 


How staleness is prevented: by construction, not by reconciliation. There is exactly one state (workProducts) and exactly one thing derives from it for reading (the papers/journeys selectors) and exactly one thing writes it to disk (the persistence adapter). There is no second store that could disagree with it, so "WorkProduct says A, legacy state says B" cannot occur post-cutover — there is no more "legacy state" being live-read anywhere.


Multiple mutation paths: all still resolve to the same setWorkProducts call inside React's state update queue — React's batching guarantees this remains a single, ordered stream of updates, same guarantee the current setPapers/setJourneys already relies on.


Asynchronous persistence / reload: the persistence useEffect fires after each workProducts change, same timing model as today's papers/journeys effects. A reload reads whatever was last successfully written — identical risk profile to today (a reload immediately after a change that hasn't yet flushed to localStorage could theoretically miss that last change; this is a pre-existing characteristic of the current app, not something Stage 3 introduces or worsens).


Failed persistence — PROPOSAL: per §12 of the brief, if saveWorkProducts throws (e.g. quota exceeded), the in-memory workProducts state has already updated (the mutation succeeded from the user's point of view), but the write failed. The adapter should return a result the caller can check ({ ok: boolean, error?} — matching Stage 2's existing console.warn-on-failure pattern, extended to also surface a toast/notice to the user via the same triggerToast mechanism already used elsewhere in the app for user-facing feedback) rather than silently claiming success. This is the minimum honest behaviour: don't build a retry queue or offline-write buffer (that's infrastructure the brief says not to invent), just don't lie about the outcome.


Partial writes: JSON.stringify + a single setItem call is atomic from the application's perspective (localStorage doesn't support partial writes within one setItem), so this class of failure reduces to the same "write failed, was reported" case above.


Imports: out of scope per §10; whenever built, it should produce WorkProduct[] entries directly (matching §10's framing) rather than legacy-shaped objects requiring a second migration pass.
